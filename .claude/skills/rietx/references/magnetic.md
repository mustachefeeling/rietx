# 7j. The magnetic family: a stated moment, its width, and the child group it implies

Load it when a magnetic `Diagnostic` fired — from a fit's `result.diagnostics`, from a magCIF/TOPAS/FullProf import, from `solve_magnetic`/`analyse_moments`, or from `magnetic_supercell`/`displacive_statement`'s returned statement — or when a distortion-mode amplitude's own support code fired instead.

*A reference file of the `rietx` skill. The body it belongs to is [`SKILL.md`](../SKILL.md); section numbers are the ones the body cites.*

Every magnetic and distortion-mode row that used to be scattered across §7 (`references/diagnostics.md`), §7g (`references/diagnostics-projects.md`) and §9b (`references/series.md`) lives here now (maintainer ruling, issue #286): one family, one file, rather than the same order-parameter question answered in three places under three different channel conventions. **The channel still varies by table, and that has not changed** — only the file it is read from:

* **Magnetic verb codes** fire on `result.diagnostics` (a fit), at import (a magCIF/TOPAS/FullProf reader — pass `diagnostics=[]` to collect it; it never reaches `result.diagnostics`), or on `MagneticSolution.diagnostics`/`MomentEvidence` rows (`solve_magnetic`/`analyse_moments`, WP-1327, provisional-by-declaration). Each row below says which.
* **Distortion-mode codes** fire on `result.diagnostics`, gated on A_τ — the order-parameter's basis-independent total (Perez-Mato, Orobengoa & Aroyo 2010, *Acta Cryst.* A**66**, 558, eq 6-7) — rather than on an individual amplitude, because an irrep fixes its modes only up to an orthogonal basis of the direction and a rotation of that basis moves an "is this one amplitude above 2σ" answer without moving the structure.
* **Isotropy/candidate codes** are not on `result.diagnostics` at all: they are on the `MagneticSupercellStatement`/`DisplaciveStatement` a builder returns, because the question — does a Hermann-Mauguin symbol name the child group this cell carries — is settled before a fit exists, the same way a project reader's own codes are.

## Magnetic verb codes

| code | what you must not assume, and what to do |
|---|---|
| `CIF_MAGNETIC_ION_UNCHARGED` | (info — from `Structure.from_cif`, pass `diagnostics=[]` to collect it; it is not on `result.diagnostics`) Assume the magnetic form factor is the one your chemistry implies. The file states no oxidation state for a magnetic site — MAGNDATA writes a bare `Mn` for a site that is chemically Mn³⁺, and magCIF has no item for the ion at all — so the **neutral atom's** ⟨j₀⟩ was used. Not cosmetic: ⟨j₀⟩ for `Mn` and for `Mn3+` are different curves, so a moment refined under the wrong one absorbs the difference into its magnitude. `where` names the site; state it with `Structure.from_cif(..., moment_ions={"Mn1": "Mn3+"})` and the code stops firing. The `suggestion` lists the ions of that element the table does carry |
| `MAGNETIC_ION_ASSUMED` | (info — same reader, same channel) Assume the neutral-atom fallback above is what fired. It is not, here: this site's bare element has **no neutral-atom row at all** — every lanthanide and actinide this table carries has only ionic ⟨jₙ⟩ curves (Brown, ITC Vol C) — so the fallback went one step further, to the element's majority oxidation state that is *magnetic* (Ln³⁺, except Eu → Eu²⁺ since Eu³⁺ is 4f⁶/J=0; Yb³⁺; U⁴⁺, Np⁴⁺, Pu³⁺ among the actinides this table's rows cover; WP-1327 D1). This is a stronger substitution than the neutral-atom one, so it fires instead of `CIF_MAGNETIC_ION_UNCHARGED`, never alongside it. `where` names the site; state it with `moment_ions={"Dy1": "Dy3+"}` and the code stops firing — the same route silences either one |
| `LANDE_G_ASSUMED` | (info — same reader, same channel; only ever alongside `MAGNETIC_ION_ASSUMED` on the same site) Assume that resolving the ion above was the whole fix. It was not: every ion `MAGNETIC_ION_ASSUMED` can produce is a lanthanide or actinide needing an explicit Landé g (`needs_explicit_g`), and magCIF has no item for g any more than it has one for the ion — so without this default the site refused one line later, on `resolve_g`, and never loaded at all (WP-1327 D-lande-g). The free-ion **Hund's-rule g_J** was used instead — `value` carries it, derived from the assumed ion's (S, L, J) ground term via g_J = 1 + [J(J+1)+S(S+1)-L(L+1)]/[2J(J+1)] (Ashcroft & Mermin, ch. 31) — because the ion is already an assumption and g is a fixed atomic-physics number for it, not a second independent guess. **Never fires for a *stated* ion** (`moment_ions={"Dy1": "Dy3+"}`): there an absent g is the caller's own gap and `resolve_g` still refuses, unchanged (issue #257 A5). `where` names the site's `.moment.g`; state it with `moment_g={"Dy1": 1.333}` and the code stops firing |
| `CIF_MAGNETIC_SYMMFORM` | (info, or **warning** — same reader, same channel) Assume the file's `_atom_site_moment.symmform` is the constraint the refinement will use — it is not. rietx derives a moment's allowed subspace from the file's own **operator list** (the operators are the model), and `symmform` is the producer's record of the same thing. At `info` the two agree on the number of free parameters, which is evidence about the file that neither side gives alone. At **`warning`** they disagree, and that is the file's operator loop and this package's symmetry algebra saying different things about one site: check which, because the fit will follow the operators. `value` is the count `symmform` states, and the message quotes the derived one beside it |
| `CIF_MAGNETIC_UNIDENTIFIED` | (info — same reader, same channel) Assume `MagneticSymmetry.uni_number` is populated. The operator list did not resolve to one of spglib's 1651 magnetic space groups, so no UNI number was recorded. The **operator list is the model and is unaffected** — the number is metadata. Three of spglib 2.7.0's own database entries cannot be matched to themselves (UNI 282, 283, 284), so a non-standard setting or one of those three reaches here legitimately |
| `CIF_MAGNETIC_NUCLEAR_SETTING` | (info — same reader, same channel) Assume `Phase.space_group`'s Hermann-Mauguin symbol is what generates the phase's symmetry. It is not, here: the nuclear group is always built from the file's own magnetic operators with time reversal dropped (`crystallography.magcif.nuclear_operations`), and this code fires when gemmi's tabulated operator table for the *symbol* disagrees with that list — an origin or setting mismatch (measured on Ima2/space group 46: MAGNDATA/Bilbao's own setting for BNS 46.245 sits at a different origin than gemmi's canonical `I m a 2` table). `Phase.space_group` is then the bracketed `"<symbol> [unnamed in this cell]"` form and `Phase.symmetry_operations` carries the derived list explicitly — the symbol is metadata, the operators are the symmetry, and nothing about the read needs fixing |
| `CIF_MAGNETIC_MAGNITUDE_ESD_NOT_STORED` | (info — same reader, same channel) Assume a `Structure` read back from a refinement CIF carries the moment's uncertainty. It does not: the file states `_atom_site_moment.magnitude_su`, and the esd of a moment's **modulus** is a property of the fit that produced it rather than of the structure, so a `Structure` has nowhere to put it. rietx keeps it in `FitReport.magnetic[i].magnitude_esd`, and `write_refinement_cif` is what writes it back into that tag. `value` is the number the file stated, so nothing is lost — it is just not on the model |
| `CIF_MAGNETIC_ANTI_TRANSLATION_RESIDUAL` | (warning — from `Structure.from_cif`, pass `diagnostics=[]` to collect it; it is not on `result.diagnostics`) Assume that because every moment passed its own site's allowed-subspace check, the whole moment set is internally consistent. It is not checked to be: the reader validates each site's moment against *that site's own* site-symmetry subspace, but never checks it against the image another operation of the *same* stated magnetic group — an ordinary rotation, a centring or an anti-translation `{1 \| t, -1}` — carries onto a symmetry-equivalent site, so a file can pass every per-site check and still state moments the group it also states does not actually leave invariant. `value` is `crystallography.magnetic.supercell.anti_translation_residual`'s worst per-component disagreement in μ_B, above 1e-6 (round-off is of order 1e-5 at worst); **not corrected** — choosing which of two disagreeing sites is right is not a reader's call, so this is reported and nothing about the read changes |

### The TOPAS and FullProf moment readers

These fire at *import*, from `rietx.io.projects` — the same channel §7g's
`TOPAS_*`/`FULLPROF_*` families use, never on `result.diagnostics` — and are
grouped with the rest of the magnetic family here rather than left in
`references/diagnostics-projects.md` (issue #286), since the question they
answer is the same order-parameter one the rest of this file answers.

| code | what you must not assume, and what to do |
|---|---|
| `FULLPROF_MAGNETIC_PHASE_OMITTED` | (warning — from `rietx.io.projects.fullprof.to_structure(..., nuclear_only=True, diagnostics=[])`) Read the returned `Structure` as the model the `.pcr` describes. You **declared** the omission by passing `nuclear_only=True`, and this says how large what you dropped is: the phase's index and name, its `Jbt`/`Isy`, its site count, how many propagation vectors it carries, which moment columns are non-zero, and its own `R_Bragg` (also on `value`). Every intensity that phase contributed is now unmodelled, so Rwp, the remaining phases' scales and every weight fraction absorb it. Without `nuclear_only=True` the build **refuses** instead: a `Jbt = 1` phase is a *pure magnetic* phase — no nuclear structure factor, its own `Scale`, a magnetic form-factor label in the species column — and rietx's magnetic model is a moment on a site of a nuclear phase sharing one scale, so the file's decomposition has nowhere to land. Its symmetry is a magnetic *representation* besides, whose matrices need not be the Shubnikov axial action ε·det(R)·R an operator list is. The route that does work: restate the phase as a nuclear phase carrying moments, which is what a magCIF states and `Structure.from_cif` reads |
| `TOPAS_MOMENT_CONVENTION` | (info — from `rietx.io.projects.topas.to_structure(..., magnetic_symmetry=..., diagnostics=[])`) Assume the moment's magnitude is TOPAS's. `mlx mly mlz` were read as **crystal-axis components in μ_B** — the magCIF `_atom_site_moment.crystalaxis` basis of unit vectors along a, b, c, which is what `Moment` stores — and that convention is **corroborated by what a moment can mean, not measured against TOPAS's own output**. The alternative reading, components in the fractional basis, would give a magnitude that depends on the cell edge in Å, which no code does for a moment; on an orthogonal cell the two differ only by a per-axis scale, so such a file cannot settle it and the message says which case yours is. What would settle it: one TOPAS run on a non-orthogonal cell. The direction is unaffected on an orthogonal cell; the magnitude is what to check against the file's own reported moment |
| `TOPAS_MOMENT_ION_UNCHARGED` | (info — same channel) Assume the magnetic form factor is the one the chemistry implies. A site carrying a moment states its species with no charge (`occ Cr` rather than `occ Cr+3`), so the **neutral atom's** ⟨j₀⟩ was used, and ⟨j₀⟩ for `Cr` and `Cr3+` are different curves. Write the charge into the site's `occ` — the reader normalises `Cr+3` to `Cr3+`, which is a form-factor key — or set `Moment.ion` on the built structure. The `.inp` sibling of `CIF_MAGNETIC_ION_UNCHARGED` |

### The refinement's own magnetic-width and evidence codes

Back on `result.diagnostics` (or the provisional `solve_magnetic`/`analyse_moments`
channel, named per row) — a fit's own account of a moment, its width and its
propagation vector.

| code | what you must not assume, and what to do |
|---|---|
| `MAGNETIC_WIDTH_UNMODELLED` | (**warning** — from a fit, on `result.diagnostics`) Quote the refined moment. The phase's magnetic reflections are drawn by peaks that are too **narrow**, and the fit has paid for it by taking the moment **down**: |F_m|² ∝ m², so shrinking the moment is the one way a narrow calculated peak matches a broad observed one's *height*, and the reported |m| is biased low by roughly the ratio of the two widths. The evidence is the residual's **shape**, never an observed-minus-calculated FWHM (this package measures no observed width): the weighted residual under the magnetic-only reflections is negative at the centre and positive in both tails, and that centre-vs-tails split is compared against the *same* statistic at the phase's nuclear-only reflections. `value` is the difference in units of its own measured noise. Differencing is what makes it safe — a wrong instrument profile, a wrong `lor_size` or a wrong background moves both sets together and cancels, so only a width that belongs to the magnetic component alone survives. Fires only while both magnetic width terms are held at zero; once one is freed the evidence is the trajectory instead (the stage that freed it is a rung on `stage_reports_`). Fix it with `phases.i.magnetic_lor_size` (and `magnetic_lor_strain` if the excess grows with angle) in the order the next row states |
| `STAGE_FREES_MAGNETIC_WIDTH_WITH_MOMENT` | (**warning** — emitted before the first stage runs, from the *plan*, on `result.diagnostics`) Read either number as a measurement of its own quantity. This stage frees a phase's magnetic broadening in the same stage that first frees its moment, and both lower the calculated magnetic peak's height — the moment as m², the width by spreading the same integrated area — so from a cold start they trade against each other and the answer is whichever pair the first step happened to like. The order is the moment with the widths held at zero (their default, which is the off state: the magnetic component is not even drawn separately), then the widths with the moment held, then both together — `plan="magnetic_width"` is exactly that, or `strategy.magnetic.MAGNETIC_WIDTH_STAGE_PATHS` as stages. And the width is only identifiable where the magnetic/nuclear intensity ratio differs across reflections: a k ≠ 0 structure with magnetic-only satellites measures it, a k = 0 collinear one generally cannot, and then it comes back with **no esd** and a named unmeasured row rather than a small number |
| `MAGNETIC_WIDTH_UNMEASURED` | (info — same channel) Quote a freed `magnetic_lor_size`/`_strain` as a magnetic coherence length. It came back below the same 3-sigma bar this package uses for a moment's modulus (no threshold of its own — the report cannot call a width measured and a moment of the same size unsupported), so the number is where the solver stopped in a flat direction. `value` is |value|/esd. The term enters the magnetic component alone, so it is identifiable only where the magnetic/nuclear intensity ratio **differs across reflections**: k ≠ 0 with magnetic-only satellites measures it, a k = 0 collinear structure whose magnetic and nuclear intensities track each other does not, and a paramagnetic pattern has no magnetic component at all. Note it comes back as an esd **larger than the value**, not as an absent esd: `unmeasured_rows` fires on an exactly zero column and this column is not zero — the pattern really does change, only the separation fails. Hold it at zero and quote the moment from that fit |
| `MAGNETIC_WIDTH_MOVED_MOMENT` | (**warning** — same channel) Drop a magnetic width because `MAGNETIC_WIDTH_UNMEASURED` called it unmeasured. The two codes answer different questions — support versus **shift** — and this one says releasing the width moved the moment by more than the moment's own error bar, so the width is *correlated with the moment*, not absent. Emitted from the trajectory, not the endpoint: the `magnetic_width` plan fits the moment at the off state in step 1 and again with the widths free in step 3, and this compares the two rungs. `value` is the shift in units of the **tighter** of the two esds (the off-state number is the one that would have been published, so its bar is the yardstick). Measured on Ba₂FeSbSe₅ at 1.5 K: the strain term back at 0.375 ± 0.283 (1.33 esd, "unmeasured") while the tied moment goes 3.908 ± 0.128 → 4.087 ± 0.18 — a 1.40σ shift, and holding the term puts the moment 0.18 μ_B low again. When both codes fire, quote the **released** moment and report the width as an upper bound (value + esd), never as a coherence length |
| `K_VECTOR_UNSEPARATED` | (info — from `solve_magnetic`, on `MagneticSolution.diagnostics`, WP-1327 provisional-by-declaration) Treat the winning propagation vector as settled without reading this diagnostic. It fires when the top two entries of `MagneticSolution.k_trials` are within `k_tie_width` BIC of each other (default 10.0) *and* the satellite step's own scoring could not separate them either — the moment refinement's intensity does not clearly favour one k over the other, and `k_trials` holds a row per k actually tried, not just the winner |
| `MOMENT_PAIR_DEGENERATE` | (info — from `analyse_moments`, on a `MomentRow`/`MomentEvidence`, same provisional channel) Read either site's own `MomentRow.magnitude`/`MomentEvidence.magnitude` for a paired row. The powder measures only the pair's quadrature sum, `sqrt(m_a^2 + m_b^2)` (`MomentRow.paired_magnitude` and `.paired_magnitude_esd`, `paired_with` naming the other site) — the two moduli are correlated in the fit and not separately determined, so either one's raw magnitude is an artefact of that correlation rather than a measurement |
| `MAGNETIC_SUBGROUP_PREFERRED` | (**warning** — from `solve_magnetic`, on `MagneticSolution.diagnostics`, WP-1418) Trust the ranked list's own top row without reading `MagneticSolution.subgroup_note`/`.subgroup_audit`. After a winner is chosen, `solve_magnetic` refits every *maximal* magnetic subgroup of the winner already reached at the same k (operator-list containment, not the DOF-count proxy) from the winner's own converged solution, and this fires when one of them beats the winner by more than `tie_width` BIC — the ranking above never considered it a competitor (it was not one of the classes `_rank` compared), and the data prefers it. `value` is the margin; the message names both groups. Re-rank by hand: this diagnostic reports the finding, it does not change `MagneticSolution.best`. When no subgroup beats the winner, `.subgroup_note` instead reads "no subgroup supported at ΔBIC < *width*" — a fact worth quoting beside a supergroup-shaped result, not only a silence to notice. Only a k = 0 winner is audited this way today; a k ≠ 0 (supercell) winner's note says the audit was not attempted, because two candidates' child cells can differ in atom count and warm-starting one from the other's solution is not yet built |
| `SEQUENTIAL_MOMENT_HOLD` | (**warning** — from `rx.refine_sequential`/`SequentialRefinement`, on `SeriesEntry.magnetic`/`result.diagnostics`) Read the held patterns as small moments, or plot them as zero with an error bar. A held point's `value` is the modulus that pattern's fit reached and its verdict is |m| against that pattern's *own* esd; `series.magnetic_trajectory()` withholds the esd there for exactly this reason. The message also names the successors whose modulus was reseeded to its floor rather than warm-started from a value the pattern before did not support |
| `SEQUENTIAL_MOMENT_ONSET` | (info, or **warning** when `MagneticOnset.bracket_verdicts_final` is False — same channel) Quote the midpoint as a critical temperature with that ± as its uncertainty. It is a **bracket** between the last released pattern and the first held one, and the ± is half the *spacing of your patterns* — no fit of `m ∝ (1 − T/T_N)^β` happens anywhere here. Two more refusals: quote it at all when the verdict is not final (a supported verdict from a fit that stopped early is a modulus that had not finished falling), and quote it as the data's onset from one pass — `direction="both"` makes the row carry both chains' brackets and say whether they overlap, and a moment carried across the transition by one chain's warm start and not the other's is invisible to a single chain |

## Distortion-mode codes

A ramp through a structural transition is the same trap one field across (§9b): a distortion-mode amplitude enters a superstructure reflection with a structure factor **odd** in A, so `|F|²` is even in A and χ² is stationary at A = 0 — an amplitude the pattern cannot see is a *flat direction*, not a small number, and the sign of A is not measurable at all (A and −A give the identical powder pattern). Gated on A_τ, not on an individual amplitude, for the reason the family paragraph above states; `FitReport.distortion[i].supported` is the same finding on the row.

| code | what you must not assume, and what to do |
|---|---|
| `DISTORTION_MODE_UNSUPPORTED` | (**warning** — from a fit, on `result.diagnostics`, gated on A_τ) Quote the amplitude as a small distortion. It fires on an order parameter whose A_τ is inside 2σ of its own esd, and the reading is that the pattern does not distinguish this superstructure from the parent — not that the distortion is small. `value` is A_τ and the message quotes the ratio, the mode count and the largest atomic displacement in Å. Two more: adjudicate one amplitude by **ΔBIC against the parent phase**, never by Rwp (Rwp improves for any added parameter), and check that the reflections the mode would create lie inside the fitted range before concluding anything at all |

## Isotropy/candidate codes

`_candidate_group`'s isotropy-subgroup construction (`crystallography.magnetic.isotropy`) is what both `magnetic_supercell` (a moment candidate) and `displacive_statement` (a mode candidate) turn into a child space group, so the one code below fires from either builder and is not on `result.diagnostics` at all — it is on the returned statement, because whether a symbol names the child's group is a fact about the candidate, settled before any fit exists.

| code | what you must not assume, and what to do |
|---|---|
| `CHILD_GROUP_UNNAMED` | (info — from `magnetic_supercell` / `displacive_statement`, on the returned statement rather than on a `FitReport`) Read the child's `space_group` as a symbol. It is a **label**: the bracketed form `'Pm [unnamed in 2a,b,a+c]'` says that no Hermann-Mauguin symbol generates this group in this cell — a parent glide's ½ along a doubled axis is a ¼ in the child, which is in no tabulated operation list — so the leading symbol names the closest *type* and generates a different group. The group is `phase.symmetry_operations`, and every orbit, multiplicity and systematic absence comes from it; the cell's metric constraints come from the closest type's point group and lattice, which are this group's own. Quote the operation list, or the type **with the cell transform beside it**. Two things such a group does not have: a Wyckoff letter (`site_constraints(...).wyckoff` is empty) and a `SPACE_GROUP_SETTING_ASSUMED` warning, both being properties of a tabulated setting. A published symbol for the same superstructure is naming a type in some other cell: check the transform before comparing. Two derivations refuse rather than proceed on an unnamed *parent* offered as somebody else's — `solve_magnetic`, `magnetic_supercell`, `displacive_statement` and `fourier_statement` all name the phase and the label rather than handing gemmi's own text four frames down (small-fixes-20260917) |
