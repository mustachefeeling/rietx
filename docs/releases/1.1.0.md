# rietx 1.1.0

**The speed milestone.** A four-phase Cu Kα refinement of the shape that
triggered this work fits in **5.69–5.72 s**, against **50.11–50.43 s**
for the same case when the milestone opened. Nothing about the physics changed
to get there. Every win carries its own equivalence bar — bit-identity where the
arithmetic is unchanged, a stated bound in esd where it is not — and none is
justified by an Rwp comparison, which
[v0.5's method result](https://github.com/yue-here/rietx/blob/main/docs/milestones/v0.5.md)
established cannot carry that weight.

Read that ratio for what it is. The "before" is the milestone's own
[opening baseline](https://github.com/yue-here/rietx/blob/main/docs/milestones/v1.1.md#appendix--the-opening-baseline-wp-1111-2026-08-20),
measured on one machine with the same harness — not 1.0.1's number, since the
baseline was taken after v1.1 opened and already carries the first WP's exact
wins. A ratio against the released version would be larger than the one quoted
here, and neither figure transfers to your machine. Both are best-of-3 on an
idle darwin/arm64 box, `[dev]` venv, Python 3.12, numpy 2.5.2.

**1.0.2 is folded into this release and was never published.** It was written,
complete and unreleased when v1.1 opened, so an upgrade from 1.0.1 crosses both
sets of changes at once. Its own notes stay as
[docs/releases/1.0.2.md](https://github.com/yue-here/rietx/blob/main/docs/releases/1.0.2.md)
for the chapter-by-chapter detail; everything a person upgrading has to act on
is in § Upgrading below, merged.

Two things need a decision before you install, and both are here rather than
buried: **numba is now a required dependency**, and **a staged refinement stops
its intermediate stages earlier by default**, which moves converged values by
up to 0.03 esd. Both have a one-line way back.

## Install

```sh
pip install --upgrade rietx
```

**numba is a core dependency from this release** (not an extra). It carries the
compiled kernel tier, which is most of the speed above: measured ~2× on a
four-phase Cu Kα refinement and ~1.35× on a synchrotron one. Two costs came
with it, both accepted deliberately on the reading that this package runs in
per-project virtual environments:

- **+157 MB** installed (llvmlite is 137 MB of it, against a ~124 MB runtime
  baseline).
- **a `numpy<2.6` ceiling**, which numba carries.

An extra could not have expressed the opposite choice — extras only ever *add*
dependencies, so "fast by default, numba-free still possible" is not a
packaging shape at all. It is a code shape instead. The import is soft and
every entry point declines rather than raising, so an install that omits numba
(`--no-deps`, a constraint file, a distro package) still works and runs the
numpy expressions, and `RIETX_COMPILED=0` switches the tier off at runtime with
no reinstall. `capabilities().features` reports both
`compiled_kernels` (is it importable) and `compiled_kernels_active` (is it on).

## What got faster

| case | v1.1 opening | 1.1.0 | |
|---|---|---|---|
| cold trigger-shaped fit — 4 phases, large cells, Cu Kα, 1 188 (line, reflection) pairs | 50.11–50.43 s | **5.69–5.72 s** | **8.8×** |
| the same model as a 10-pattern warm-started series | 266.78–269.61 s | **49.24–49.30 s** | **5.4×** |

Best-of-3, idle darwin/arm64, `[dev]` venv, Python 3.12.12, numpy 2.5.2. Rwp
is an identity check between *repeats of one case*, never the metric and never
a comparison between the two columns — across the milestone it moved 0.01979 →
0.01998 on the cold fit and 0.01927 → 0.01943 on the series, which on these
simulated rows is counting noise. The per-WP equivalence bars below are what
say a fit did not change; each is stated in its own terms because they are not
the same kind of claim.

Inside that series the per-pattern picture matters more than the total, because
the distribution has two modes rather than one. Seven of the nine warm patterns
run in **0.88–2.33 s** (median 2.02). Two do not: pattern 6 at 10.53 s and
pattern 1 at 20.26 s, both of them patterns whose first ladder rung is rejected
and refit. The opening baseline was 4.5–22.4 s for *every* warm pattern.

Where it came from, each with the bar it was held to:

- **The plane seam runs batched** (WP-1120). The numpy forward evaluates
  whole reflection planes instead of looping reflections. Bit-identical
  wherever the rows are symmetric — identical per-stage `nfev` *and* Rwp on
  four cases — and one ulp where they carry FCJ.
- **A compiled tier under the numpy path** (WP-1115), and it is what a default
  install runs. It is *not* a fourth backend: jax and torch keep the traced
  twin and nothing above `compile_model` branches on whether the kernels ran.
  The gate opened on fusion and threading rather than on dispatch — three
  kernels fused over `nogil` on a shared thread pool. The scatter is
  bit-identical; symmetric rows are too, in window; FCJ rows keep the batched
  path's rounding bar. Cold JIT costs 0.60 s, 0.12 s cached, and is warmed in
  the background from `compile_model`.
- **The fast tolerance schedule, on by default** (WP-1123). Intermediate stages
  of a staged plan now stop at `ftol=1e-6` against the solver's 1e-9; the last
  stage is the one that converges. This is the change that moves numbers, and
  § Upgrading says by how much.
- **The phase-scale Jacobian column in closed form** (WP-1121). The model is
  exactly linear in a phase scale, so the column is written rather than
  finite-differenced. **Exact, not bit-identical** — it moves every converged
  fit that frees the parameter, and it moves it toward the truth. The
  whole-model FD is the wrong oracle for a transformed parameter and would have
  certified the column being replaced.
- **The ladder's first rung is priced** (WP-1127). In a warm-started series a
  rejected fit escalates a rung at a time, and a losing first rung does not
  cost more than a winning one, it costs the whole budget. `first_rung_factor`
  (default 3.0) bounds it at three times the dearest first rung the chain has
  already converged, and bounds nothing until three have. Answers are
  **bit-identical** on both series cases measured — 0 of 1030 and 0 of 392
  accepted values differ — because a bound only truncates a rung whose result
  is discarded.

Three probes closed negative and are recorded that way rather than quietly
dropped: predictor seeding of a warm chain (WP-1124), variable projection of
the background (WP-1125), and the peaks buffer (WP-1114, retaken as WP-1122 on
the compiled tier). The buffer does pay where peaks are FCJ-smeared, 1.9–2.8×
on the plane seam, but the plane seam is 54.9 % of the cold fit — so a *free*
one still leaves 2.56 s, and it now ships with FPA, which is what raises the
images-per-window-point multiplier its break-even is in.

## What a fit answers differently

Four changes move numbers a 1.0.1 user could be reading. None of them is a
change of physics; three are repairs, and one is a default.

- **A direction the data does not move now reports no esd rather than a small
  one** (WP-1110). The normal matrix is equilibrated (Jacobi-scaled, van der
  Sluis 1969) before it is inverted. `pinv` cuts every eigenvalue under
  `rcond × |λ|max`, so before this the *largest* column set the cutoff for all
  of them and a flat direction came back at **zero** variance — a confident
  wrong singleton wearing an esd. A gradient-free column is now infinite
  variance, which is true and unpropagatable, so it is dropped and named:
  `ParameterTable.unmeasured_rows` says what it reached, a tie inherits its
  source's blindness, and consumers **mark rather than clamp**.
- **A phase the data cannot see gets a per-stage cell window** (WP-1110). Such
  a phase reaches the pattern only through `scale × |F|² × profile`, so one
  whose scale sits at its floor moves nothing: the fit reported `converged`
  while the cell walked out of the physical range and the run died hundreds of
  stages later in `generate_reflections`. The window applies to **that phase
  only** — TRF takes its trust-region scale from the distance to the bounds, so
  windowing every phase changes the step in cells that never reach one.
  `PHASE_UNCONSTRAINED` names the cause.
- **Intermediate stages stop earlier** (WP-1123). See § Upgrading.
- **The extinction screen's answer can change** (WP-1077, written for 1.0.2).
  Writing the manual chapter over it found it refuting a certified space group.
  On data where a neighbouring peak's tail reaches a forbidden position, a
  class it refuted may now survive and win.

## Everything 1.0.2 carried

1.0.2 was a documentation release on the 1.0.x road, and its substance arrives
here. **No forward model, solver or statistic changed in it**, so its two
source-visible changes are the ones listed above and below rather than a
different set.

- **Five new Part 1 chapters**: patterns/structures/instruments, the parameter
  table, running a refinement, the refinement history, and indexing an unknown
  cell. They are reference chapters, and a reference manual's failure is a
  name, so every dotted name and dot-path in them resolves and every python
  block parses and either runs or carries a written reason.
- **1044 names left the provisional bucket.** Documenting a name is what froze
  it, and the chapters divide them: 170 for patterns and structures, 29 for the
  parameter table, 71 for refining, 117 for history and projects, 83 for series,
  49 for phase analysis and exports, and so on. The chapter-by-chapter count is
  in [1.0.2's § The freeze](https://github.com/yue-here/rietx/blob/main/docs/releases/1.0.2.md#the-freeze).
- **Indexing is documented in full — 257 names — and freezes none of them.** The subsystem is **declared provisional** as a whole, by
  module rather than by list, so a type written under `rietx.indexing` or
  `rietx.schemas.indexing` after this release inherits the declaration. What is
  *not* covered is stated with it: `Capabilities.indexing_thresholds_version`
  and the agent envelope's `indexing` arm are versioned contracts and keep
  their hard freeze.
- **Two result fields nothing ever wrote are gone**, and one now answers a
  question instead of defaulting to an answer (`at_bound`). § Upgrading has
  each.
- **The backward chain is reachable from `refine_sequential`** as
  `SeriesResult.backward`.

Since 1.0.2 was drafted, the compatibility promise itself became a **preview**
(WP-1117): anything may change in any release, and any change a consumer could
observe bumps its contract's last component by one, with the comment beside the
constant saying what. Documenting a name still gates its arrival; it no longer
freezes it.

## Contract versions

Six versioned contracts, and `capabilities()` is where a program reads them
rather than this table. Four moved since 1.0.1:

| Contract | 1.0.1 | 1.1.0 |
|---|---|---|
| `schema_version` | 0.1 | **0.5** |
| `report_thresholds_version` | 1.1 | **1.3** |
| `project_format_version` | 1.1 | **1.2** |
| `indexing_thresholds_version` | 1.2 | **1.3** |
| `event_schema_version` | 2 | 2 |
| `textdoc_format_version` | 1 | 1 |

`schema_version` moved four times and each step's comment sits beside the
constant in `schemas/common.py`: 0.2 removed the two unwritten fields; 0.3
added `StageSpec.window_slack_deg`; 0.4 added `StageSpec.ftol`; 0.5 added
`PlanSpec.intermediate_ftol` **defaulting to 1e-6**, plus `StageResult.ftol`
and `NodeAction.ftol`/`window_slack_deg` recording what a stage ran at. 0.5 is
the one entry so far whose *default* changes an answer rather than only the
field list.

## Upgrading

Who has to do something, and what.

- **You run a staged plan and compare converged values against 1.0.1's.**
  Intermediate stages now stop at `ftol=1e-6`. Measured on the harness: 1.2–1.6×
  fewer whole-plan evaluations, Rwp equal to five decimal places, and the widest
  non-degenerate parameter move **0.027 esd**. The bound is ≤ 0.03 esd and it
  holds for **one fit**, not for a chain — in a warm-started series each pattern
  seeds the next, so the effect is unbounded and not even fixed in sign
  (measured both ways, 1.12× better and 1.04× worse, one commit apart). A series
  is measured, never assumed. `RefinementPlan.intermediate_ftol=None` is the
  bit-identical way back, and it is what a golden should declare.
- **You have a warm-started series with a golden trajectory.** WP-1127's first
  rung bound is on by default:
  `SequentialRefinement.fit(first_rung_factor=3.0)`, reachable through
  `refine_sequential`'s `**kw` as well. Accepted values were
  bit-identical on both series measured, but the bound is a wall-clock quantity
  and this is the honest place to say that `first_rung_factor=None` is the
  unconditional way back.
- **You read an esd on a parameter the data does not constrain.** It is now
  absent rather than small. Code that assumed every refined row carries a number
  needs a `None` branch; `ParameterTable.unmeasured_rows` says which rows and
  why.
- **You refine a phase that may be absent from the specimen.** Its cell now
  carries a per-stage window and the fit reports `PHASE_UNCONSTRAINED` instead
  of converging quietly and dying later. A finite stored bound is your own claim
  and suppresses the window on that side, so pass **no** floor rather than a
  nonsense one.
- **You pin `numpy>=2.6`, or you install into a constrained environment.**
  numba's ceiling is now the package's. See § Install for the two escapes.
- **You read `RefinedParameter.initial` or
  `RefinementResult.correlation_warnings`.** Both are removed. Neither was ever
  written, so whatever you read was `None` or `[]`. Delete the code. For a fit's
  starting values use the history tree — the node above the stage holds the
  state it started from. For correlations read the `HIGH_CORRELATION`
  diagnostics or `RefinementResult.identifiability`.
- **You load a result JSON written by 1.0.0 or 1.0.1.** The schemas are
  `extra="forbid"`, so an older file's `"initial"` and `"correlation_warnings"`
  keys are now rejected rather than ignored. Strip the two keys, or re-run the
  fit. A history tree is unaffected: it stores state, not results, and nothing
  in the package gates on the version stamp.
- **You call `TieSpec.from_tie`.** It is now `TieSpec._from_tie` and private. A
  `TieSpec` still arrives ready-made on `ParameterRow.tie`.
- **You branch on `at_bound`.** It is three-valued. `if row.at_bound:` still
  means what it meant; `if not row.at_bound:` no longer does, because `None` is
  not the same claim as `False`. Compare against `is True` / `is False` where
  the distinction matters, which on a tied row it does.
- **You match exhaustively on `StageResult.status`, `NodeMetrics.status` or
  `NodeAction.kind`.** Delete the `"skipped"` and `"lebail_update"` branches. No
  writer ever produced either, so no branch you delete was ever taken.
- **You branch on `AgentError.code`.** A missing optional backend now returns
  `BACKEND_UNAVAILABLE` where it returned `REFINEMENT_FAILED`, and an
  unsupported feature combination returns `REFINEMENT_FAILED` where it returned
  `BACKEND_UNAVAILABLE`. Both are corrections toward what the codes are
  documented to mean.
- **You read a series table by column name.** The default header's third column
  is `x` rather than a second `index`. A reader keying by position is
  unaffected; one keying by name was reading pandas' `index.1`.
- **You read `ExtinctionCandidate.n_testable`.** It is `int | None`, and `None`
  until `ExtinctionCandidate.screened` — the count needs that class's own fit,
  so before it the answer is unknown rather than zero. `if not n_testable:` no
  longer separates "the data can test none of these" from "nobody asked";
  compare against `0`, or read `screened` first.
- **You act on an `ExtinctionScreen`.** Its answer can change on data where a
  forbidden position falls under a neighbour's tail. Nothing else in the package
  reads it, so a pipeline that stops at `index_pattern` is unaffected.
- **You save a `.rex` project here and open it with 1.0.x.** The persisted plan
  gained `intermediate_ftol`, which an older build's `extra="forbid"` refuses.
  The major gate still opens every 1.x; what the minor bump records is that the
  vocabulary grew.
- **You import an indexing type or call.** They are documented and
  **provisional**, so pin a version if you build on them. Reading an answer is
  unaffected: `Capabilities.indexing_thresholds_version` and `refine_json`'s
  `indexing` arm are versioned contracts and move by the same rules as before.

Nothing else moves a refinement's answer beyond the four entries in § What a fit
answers differently.
