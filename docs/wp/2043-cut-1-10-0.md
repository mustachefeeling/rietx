## Goal

`docs/releases/1.10.0.md` names every user-facing change in `v1.9.0..main`, or
the handover says why one owes no note. `pyproject.version` reads `1.10.0`, the
three pre-upload nightly jobs are green on the release commit, and
`docs/milestones/v1.10.md` carries the ship block. The macOS split in the QPA
guide's esd is either shown to predate 1.10 or fixed before the tag. What
remains after that is `RELEASING.md` steps 5-7: the tag, the `pypi` approval
and the check from the index.

## Context

**The range at the open.** 1.9.0 was tagged on `ea1800d3` on 2026-10-14.
`v1.9.0..6fe7a5bb` holds 876 non-merge commits and 120 first-parent merges.
The session-start hook counts 181 merge commits, because it also counts
merges of `main` into branches. The staged notes are 32 425 bytes, and every
session that landed a change since 1.9.0 has written into them and into the
v1.10 record.

**The nightly at the open.** `RELEASING.md` step 4 gates the upload on three
nightly jobs: `fast suite (Windows)`, and the Linux fast suite on Python 3.12
and 3.13. Linux was green on all four nightlies from 2026-10-20 to 2026-10-23.
Windows was red on all four, for three reasons, none in a shipped path:
- `tests/test_closed_wp_writes.py`, five tests of the dev hook
  `.claude/hooks/closed_wp_writes.py`. Its `_git` runs `subprocess.run(...,
  text=True)` with no encoding, so Windows decodes git's output as cp1252. The
  ✅ glyph's UTF-8 bytes decode to `âœ…`, `STATUS_RE` misses it, and no WP
  reads as closed. Read from the code, not run on Windows.
- `tests/test_manual.py::test_the_page_contract_fails_what_it_should`. One
  parameter is a 60 000-character page, pytest copies the test id into
  `PYTEST_CURRENT_TEST`, and Windows refuses an environment variable over
  32 767 characters. It errors at setup and teardown.
- `test_examples.py::test_every_guide_script_prints_what_its_page_quotes[moment]`
  printed other numbers on Windows on 2026-10-23 (`3e0dc6f7`). WP-2002's
  `b3ff7c1e` re-pinned the page to what every platform shares, after that
  nightly. No nightly has run on a tree holding it yet.

**The macOS split in the QPA guide.** The nightly's macOS job is not a gate,
but on `3e0dc6f7` it printed CaF₂ 3.08 ± 0.21 wt% from
`examples/guides/qpa.py`'s first fit, where the page quotes ± 2.24. Linux
prints 2.24. So does a local arm64 Mac (darwin 25.6), both with numpy 2.4.6 and
scipy 1.17.1 on Python 3.12 and with the runner's numpy 2.5.4, scipy 1.18.1 and
Python 3.13 (`6fe7a5bb` snapshot). The runner image was `macos-26-arm64`,
macOS 26.6.2. Measured locally on that fit: `phases.1.extinction` 1361 ± 2116
(`stderr_uncorrected` 242, so the Bérar-Lelann factor is 8.7), and no stage
took a LAPACK fallback. Dropping that factor alone would print ± 0.26, so it
is not the whole story. The fraction agrees on every platform. Only its esd
differs, by 10.7×.

The 2026-10-22 macOS nightly (`d01ae735`) passed the QPA guide, but its tree
did not yet hold WP-2002's `e5976784`, which re-pinned the page for the
closing stage. So the split first shows on a tree holding #1085 (WP-2002's
closing stage, esd reporting and `optimize/lapack.py`). 1.9.0 has no QPA guide,
so whether 1.9.0's same fit splits is unmeasured.

**The maintainer's ruling, 2026-10-24.** Option B of three: do the cut work
now, fold the two Windows fixes in, and check the split on the macOS runner
under 1.9.0 and under main before the tag. If 1.9.0 splits too, the split is
not a regression and gets its own WP. If only main splits, its cause is found
and fixed before the tag. A silent wrong answer in a shipped path is P1 by
`TEMPLATE.md`'s rubric, which would owe an immediate patch release.

**The kernel wheel.** WP-1997's record (2026-10-23) leaves `kernels-v1.4.0`
to the maintainer: the crate is at 1.4.0 on `main`, PyPI has 1.3.0. rietx's
floor is still `rietx-kernels>=1.3,<2` and nothing in rietx calls the 1.4
kernels, so this cut does not wait for that wheel.
